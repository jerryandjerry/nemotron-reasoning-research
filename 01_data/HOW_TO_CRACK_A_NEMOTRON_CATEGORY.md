# How to Crack a Nemotron Puzzle Category — From Scratch

## The landscape (what a "category" is)

Each Nemotron category is a family of puzzles generated by one rule set. For any category `X` you will
typically find:

- **Raw puzzles** — a `question.txt` (the prompt: a few examples + one query) and a stored `answer.txt`
  per puzzle, and/or reference CoT CSVs (look under `01_data/` for `*_cot_<X>.csv`).
- **A reference reasoner** — `reasoners/<X>.py` in the reference solver snapshot under `02_train/`. **This
  is the single most important artifact**: the puzzles are *generated* by it, so it encodes the exact rule
  space (every operation, every noise form, every degree of freedom). Reading it is the fastest honest path
  to understanding the mechanics.
- **The official metric** — last `\boxed{}` extraction + a 3-branch verify. Documented once in
  [`../ANSWER_EXTRACTION.md`](../ANSWER_EXTRACTION.md); reuse it verbatim.

> **Crucial distinction:** the reference reasoner runs **forward** (choose the hidden rule → emit the
> equations). Your job is the **inverse** — given the equations, *deduce* the hidden rule and narrate that
> deduction honestly. The reasoner hands you the rule space; it does **not** hand you the deductive method.
> You design that.

## The 8 phases

### Phase 0 — Orient
- Locate the category's raw puzzles, the reference reasoner (`reasoners/<X>.py`), and the reference CoT CSVs.
- Confirm the deliverable: one CoT per puzzle, written to that puzzle's `track/tree_cot.txt`.
- Confirm the metric ([`../ANSWER_EXTRACTION.md`](../ANSWER_EXTRACTION.md)) — you will reimplement it so the
  generator can self-score.

### Phase 1 — Reverse-engineer the latent rules  ← **the hard part; budget most of your time here**
This is where the real intellectual work is. The output of this phase is a precise written model of the
puzzle: the rule vocabulary, the degrees of freedom, and every edge case.
- **Read `reasoners/<X>.py` closely.** It defines exactly what transformations exist and how the answer is
  produced. Enumerate: the base operation(s); any *noise* (off-by-k, sign forms, reversals); any global
  degree of freedom (reading direction, orientation, ordering); how malformed-looking inputs arise; how the
  query answer is computed and formatted.
- **Cross-read a sample of raw `question.txt` + `answer.txt`** and the reference CoTs to see the rule space
  *in the wild* and to learn the conventions.
- **State the consistency lever.** A candidate rule is valid only if it fits **every** example in the
  puzzle — that constraint is what makes deduction possible. Find the structural property that lets you
  solve unknowns **independently** rather than searching all combinations (for equation_numeric it was the
  distinct-operator rule; every category has some such lever — find it and write it down).
- **Catalog the cases you must handle deterministically:**
  - the *determined* case (rule is uniquely pinned by the examples);
  - the *underdetermined / ambiguous* case (several rules fit and disagree on the query → you need a fixed,
    explainable **prior**, applied identically everywhere — never a coin flip);
  - the *out-of-vocabulary / exotic* case (no modeled rule fits → a single hardcoded, observed guess, same
    status as boxing a fixed number);
  - the *malformed-signal* edge cases (e.g. for equation_numeric a leading zero or a sign in the output is a
    legality signal — find this category's analogues).
- **Use the reference material to UNDERSTAND, never to copy.** Do not transcribe the reference reasoner's
  forward logic or another solver's CoT into yours, and never credit or name another solver. Build your own
  honest deductive method and verify it against the raw data.

### Phase 2 — Design a deterministic, forward-only solver
- Model it as a **constraint-propagation state machine**: a candidate set per unknown; each step either
  **prunes** a set or **locks** it to one value, and passes the updated state forward.
- **Forward-only**: every decision uses only what earlier steps established. Never peek at a later step or
  the answer.
- **Greedy + backtracking** where the consistency lever allows: lock the first consistent value, verify on
  the remaining examples, advance on failure.
- **Determinism**: when the puzzle is underdetermined, resolve with the fixed prior from Phase 1 — explained
  the same way in every puzzle. Guessing is allowed *only* when nothing is deducible, and the guess must be
  deterministic and explainable. **Any random choice scores 0.**
- Put the edge-case handling in as explicit, ordered **gut-checks** (cheapest first).

### Phase 3 — Write the CoT as a SYSTEM LOG
- The CoT is a **literal log of the solver running**: do a step → print what it did → print the resulting
  state; repeat. No refinement, no cover, no fake prints, no leakage. (This is the governing principle — see
  the worked version atop [`260523_Numeric_Equation/cot_template.md`](260523_Numeric_Equation/cot_template.md).)
- **Controlled vocabulary**: a fixed set of line-templates; the *same condition produces 100% identical
  wording*. Write these into a spec doc (the `cot_template.md` analog) that the generator must match
  line-for-line.
- **Pin every special character to a tokenizer ID.** Build a sign/character legend and check the real
  tokenizer for collisions (look-alike Unicode chars, separators that tokenize to a meaningful token). This
  is invisible unless you check — see [`260523_Numeric_Equation/LESSONS.md`](260523_Numeric_Equation/LESSONS.md) §C
  for the minus-sign collisions that bit equation_numeric.

### Phase 4 — Build the generator
- **One script** (`_gen_eq.py` analog): reads the input, runs the Phase-2 solver, writes one CoT per puzzle
  to `track/tree_cot.txt`, and prints the score.
- **CoTs are ONLY generated, never hand-edited.** To change a CoT you change the generator and regenerate.
- Keep the generator and the spec doc in lock-step — they must always agree.

### Phase 5 — Wire up the metric (as a sanity signal only)
- Reimplement the official extraction + verify ([`../ANSWER_EXTRACTION.md`](../ANSWER_EXTRACTION.md)) inside
  the generator and print `OUR <metric>: N/total`.
- **It is a sanity signal, full stop.** The stored answers are *not* ground truth. The metric must never
  drive or justify a logic choice, and a choice is never "correct" because it matches the stored answer. The
  only correctness criterion is honest + forward-only + deterministic + spec-faithful (Phase 6 checks this).

### Phase 6 — Audit (the real correctness check)
- Shard the puzzle IDs into ~10 lists.
- Launch ~10 **fresh, no-context reviewer agents in parallel** (one per shard). Each reads the spec + review
  rubric, then for every puzzle reads `question.txt` + `track/tree_cot.txt` and **recomputes every line by
  hand** — never trusting the CoT. They score 0–10 and report a table + a defect list.
- **Reviewers must be independent** — an author auditing their own output is blind to their own leaks.
- Goal: **every puzzle 10/10.** The exact sharding command and reviewer protocol are in
  [`260523_Numeric_Equation/README.md`](260523_Numeric_Equation/README.md) §6.

### Phase 7 — The feedback & improvement loop
For every defect (from the audit or flagged by the human):
1. Surface it to the human with a **clickable puzzle link** + the exact offending lines + the root cause,
   and **wait for the human's fix direction. Do not implement a fix unilaterally** — several "obvious" fixes
   were wrong and got redirected.
2. Fix in the **generator only**; keep the spec doc synced.
3. Regenerate and **verify**: score holds (unless logic genuinely changed); **diff boxed answers vs the
   pre-fix baseline** (a narration-only change must move zero answers — prove it); enumerate the scope by
   grepping for the changed line; hand-read every changed puzzle.
4. **Log the defect** (root cause + fix + scope) in the review-rubric doc as a permanent changelog entry.
5. **Re-run the full audit** to re-clear the whole set.
The verification techniques (answer-diff, baseline reconstruction in `/tmp`, scope enumeration) are spelled
out in [`260523_Numeric_Equation/README.md`](260523_Numeric_Equation/README.md) §7.

### Phase 8 — Document for handoff
Produce, in the category's folder, the same four artifacts this method produced for equation_numeric:
- a `README.md` (index: problem, pipeline, process, reproduce steps),
- a `LESSONS.md` (dead ends with *why*, leakage traps, tokenizer landmines, rationale, gotchas),
- the spec doc (`cot_template.md` analog),
- the review rubric + defect log (`agent_review_instruction.md` analog).

## Cross-cutting hard rules (govern every phase)

1. **The CoT is a system log, not a polished explanation.** "Can you print a fake system log?" — no.
2. **Forward-only.** A line uses only values derived above it. Never pre-compute a later step's result.
3. **Honesty over score; stay true to the logic even if points are lost.** The metric is a signal, never the
   target, never a justification.
4. **Deterministic.** Same logic everywhere; guess only when nothing is deducible, and deterministically.
   Random = 0.
5. **Same condition → identical wording.** The generator's line-templates are the controlled vocabulary.
6. **One shared routine per concept** — no special-case shortcuts.
7. **Human-directed fixes** — surface with a link, wait; don't go solo.
8. **Edit the generator, never hand-edit a CoT.** Don't touch user-managed config/env files.

## Leakage traps (the dishonesty patterns to watch for — category-agnostic)
- Using a later step's result in an earlier line (the answer, a sign, a downstream check).
- Asserting one branch's conclusion while narrating another branch.
- Sufficiency/correctness verdicts ("too few examples", "this is a guess", "X also fits") — only knowable by
  peeking at the answer. Forbidden.
- Mentioning alternatives the trace never actually tested.
- Calling a choice "correct"/"accurate" because it matched the stored answer.
The antidote is always the same: **print the real running state, step by step. Don't fear honest mistakes —
the fresh reviewers recompute every line.** ("Be stupid, don't be smart.")

## Definition of done (checklist)

- [ ] Phase 1 rule model written down (vocabulary, consistency lever, ambiguous/exotic/edge cases).
- [ ] Generator produces a CoT for every puzzle; CoTs are 100% generated, never hand-edited.
- [ ] Spec doc exists and the generator matches it line-for-line; sign/char legend checked against the real tokenizer.
- [ ] Metric reimplemented and printed — and treated as a signal only.
- [ ] Full fresh-reviewer audit run; **every puzzle 10/10**.
- [ ] Every defect logged with root cause + fix + scope; re-audited clean.
- [ ] Handoff docs written (README, LESSONS, spec, review rubric).
